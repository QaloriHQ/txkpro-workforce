## Ownership and access

An active canonical application user owns their AuthCard and private reusable screening details. `security.pro_actor()` derives that user from the authenticated session. No client user ID or editable auth metadata grants access. Private details are an allowlisted AES-256-GCM blob using the existing server-only encryption key with candidate-specific AAD. Saved SSNs are masked on owner reads and retained on blank editor submissions. These details are candidate-entered claims, not Stripe-verified fields. Names, addresses, SSNs, DOB, ID images and Stripe data are never part of the employer card projection. Stripe sensitive DOB is used transiently for an adult eligibility boolean; raw verified outputs/documents are not retained or redistributed. The platform test verification state is distinct from instructor credentials, skills, readiness, background clearance and employment eligibility. Test mode never claims genuine identity proof.

Workspace requests require existing explicit screening order permissions, active subject scope, fixed prices, fee-inclusive budgets and independent approval where configured. Each request is bound to a subject/order/cart/price, canonical named workspace, purpose, explanation and orderer certification. Operational institution users and employer applicants/employees are supported by the existing subject rules. Ordinary students/employees cannot order checks. The `authcard_order_status` projection reuses existing session/scope authority and reveals only shared platform status and order authorization. No public AuthCard endpoint is provided.

## Workflow and state

1. Owner prepares private information at `/account/authcard` (Student Home and Employee navigation link there). All forms use shared button-triggered dialogs.
2. Pay or resume one $5 **test** KYU platform fee. Stripe Identity capability is checked before creating a charge. One stable Checkout Session idempotency key/lease binds the card; invoice and receipt links are obtained from that exact session. Fee is separate from workspace check payments/reward credits.
3. Complete document + matching-selfie verification via Stripe's secure modal. Explicit adult confirmation and an adult candidate-entered DOB are required before starting. Provider-retrieved DOB must also establish 18+ before verification becomes active. US minors remain denied. One session/lease/idempotency key is retained; missing/ambiguous provider responses require same-session resume/reconciliation, not another charge/session.
4. Authorized workspace orderer selects a transaction purpose and separately certifies authorized-transaction use and no employment/credit/insurance/FCRA eligibility use **before** candidate sharing. The optional description is bounded. Purpose choices reflect documented Authenticate transaction uses, not an official approval menu.
5. Candidate sees the named workspace and exact checks/price/purpose. Sharing grants only that request's platform identity status. Share and check authorization are separate actions; decline/revocation block further access.
6. Candidate reviews all named required parties/disclosures, initially unchecked. Check all/Uncheck all affect only displayed fields. Backend requires the exact current party set/version; one immutable snapshot records scope, candidate, products, price, purpose, orderer, disclosure text/version, accepted party IDs and time. The first authorization refreshes the frozen quote's 30-minute checkout window. Changed disclosures require a new order, not rewriting consent.
7. Both checkout and every provider claim require active verified/adult/paid KYU, prepared details, shared grant and exact current order authorization. Existing orderer/reviewer/scope/payment/budget checks still run. Refunds/disputes freeze KYU. Revocation/deactivation stop future submissions; already submitted checks and historical authorization cannot be recalled.
8. Workspace embedded test checkout, invoices/receipts, independent payment observation, mock check completion and internal costs reuse #244. Existing interview/offer/pending_start/actual-start placement and retention rules are untouched.

KYU states: `not_started`, `requires_input`, `processing`, `verified`, `cancelled`, `revoked`. KYU payment states: `unpaid`, `pending`, `paid`, `hold`. Share states: `pending`, `shared`, `declined`, `revoked`. Consent read states: `pending`, `authorized`, `changed`. Consent is an immutable record, not an editable lifecycle. Events are `AUTHCARD_SHARE`, `AUTHCARD_DECLINE`, `AUTHCARD_REVOKE`, `AUTHCARD_AUTHORIZE`, `AUTHCARD_DEACTIVATED`, and service `AUTHCARD_DETAILS`, `AUTHCARD_PAYMENT_BIND/OBSERVE`, `AUTHCARD_IDENTITY_BIND/OBSERVE`. Events retain IDs/state only, never raw payloads. Provider observations replay without duplicate state-change audit entries. Deactivation is terminal for this first release; support-assisted re-verification is a follow-up.
