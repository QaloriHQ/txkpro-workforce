TXKPRO™ WORKFORCE
DATA OWNERSHIP, SOURCE-OF-TRUTH & SCOPE RULES
Version 1.0 — September 2026

PURPOSE
Define which domain owns each data class, who may change it, and which apps may see it.

GENERAL RULES
1. Supabase/Postgres is the shared canonical backend.
2. Apps are role-specific interfaces, not separate systems of record.
3. Authentication identity is distinct from application roles.
4. Role + scope determine authorization.
5. Self-attested data must retain its provenance.
6. Institution verification must never be overwritten by student edits.
7. Employer-private hiring notes never become Institution/Student data.
8. Institution-private educator notes never become Employer data unless explicitly shared.
9. Collect minimum necessary readiness information.
10. Raw screening/MVR/drug-test records are out of MVP1 scope.

DATA CLASS: AUTH IDENTITY
Canonical owner: Supabase Auth
Writers: Auth system/user auth flows
Readers: server auth layer; apps receive safe identity context
Key: auth_user_id UUID

DATA CLASS: APPLICATION USER
Canonical owner: TXKPRO shared user record
Writers: trusted server workflows/admin
Readers: role apps according to policy

DATA CLASS: ROLE MEMBERSHIP
Canonical owner: shared authorization model
Writers: authorized Institution/TXKPRO/Employer administration workflows
Readers: server authorization layer
Client UI must not grant membership.

DATA CLASS: INSTITUTION / PROGRAM / COHORT
Canonical owner: Institution domain
Writers: authorized institution administrators/program leadership
Readers: Institution; Student own affiliation; Employer permitted cohort metadata; Admin

DATA CLASS: STUDENT PROFILE
Canonical owner: Student domain with institution-linked fields
Student may edit: personal/work preferences and allowed contact/profile fields
Institution may manage: institution/program/cohort linkage and approved workforce fields
Employer may read: only discoverable/permitted fields
Admin: policy-authorized operations

DATA CLASS: STUDENT READINESS
Canonical owner: Student workforce profile
Self-attested fields: student writes
Institution-verified fields: authorized institution writes verification/provenance
Employer: reads permitted fields with source labels
Never imply self-attestation equals insurance/background clearance.

DATA CLASS: SKILL CATALOG
Canonical owner: Institution/program domain
Writers: authorized institution curriculum/workforce roles
Readers: Student, Employer, Institution, Admin as allowed

DATA CLASS: STUDENT SKILL SELF-ATTESTATION
Canonical owner: Student skill record
Writer: Student
Institution reads for verification queue
Employer may read only if product policy exposes it and it is labeled self-attested.

DATA CLASS: SKILL VERIFICATION
Canonical owner: Institution verification record
Writers: authorized instructor/approver
Student cannot alter verified_by, verified_at, verified state.
Employer reads verified state where candidate is visible.

DATA CLASS: EMPLOYER PROFILE
Canonical owner: Employer domain
Writers: employer admins/owners; TXKPRO approval fields by TXKPRO
Institution sees approved partnership/hiring information, not private company operations.

DATA CLASS: HIRING REQUIREMENTS
Canonical owner: Employer
Writers: authorized employer users
Institution may read requirements intentionally shared for referrals.
Student may see opportunity-level requirements where applicable.

DATA CLASS: REFERRAL
Canonical owner: Shared placement workflow
Creator: authorized Institution role
Employer controls employer-side action state where appropriate.
Student sees own referral state.
Institution sees institution referral lifecycle.
Admin sees operational/audit metadata.

DATA CLASS: INTERVIEW REQUEST
Canonical owner: Shared hiring workflow
Creator: authorized Employer
Student controls own response
Institution sees outcome for institution-linked student as permitted
Employer owns employer-side scheduling details
Private interview evaluation notes remain Employer-only.

DATA CLASS: PLACEMENT
Canonical owner: Shared outcome record
Creation/update: authorized Employer or permitted workforce operator
Institution sees its student's outcome
Student sees own placement
Admin sees platform outcome
Placement creation triggers retention milestones.

DATA CLASS: RETENTION RESPONSE
Canonical owner: Retention workflow
Writer: Student response / messaging system
Institution/Career Services sees intervention-relevant information
Employer visibility is policy-controlled and must not expose sensitive case notes by default
Admin sees operational state.

DATA CLASS: RETENTION CASE
Canonical owner: Institution/TXKPRO intervention workflow
Writers: authorized Career Services/Admin roles
Student may receive follow-up but does not edit internal case notes
Employer receives only explicitly approved information

DATA CLASS: AUDIT EVENT
Canonical owner: Platform audit subsystem
Writers: server/system only
Readers: authorized administrators/analysts
Immutable in normal UI.

DATA CLASS: REPORTING METRICS
Canonical owner: derived from canonical domain events/records
Do not manually store contradictory summary numbers where they can be computed.
External benchmark statistics must be labeled separately from TXKPRO telemetry.

TENANT ISOLATION RULES
- Institution membership never grants access to another institution.
- Employer membership never grants access to another employer.
- A shared Supabase project is acceptable only with enforceable row/scope authorization.
- Host/subdomain is not authorization proof.
- Every object mutation revalidates actor scope server-side.

DATA MINIMIZATION
MVP1 excludes:
- FAFSA/Pell/financial-aid data
- raw academic transcripts unless separately approved
- raw MVR/driving reports
- raw background-check reports
- drug-screen reports
- medical data

EXPORT RULES
- Exports re-check role/scope server-side.
- Export is audited.
- Analyst access can be aggregate-only.
- Employer export cannot include Institution-only data.
- Institution export cannot include Employer-private hiring data.

END

D-10 APPROVED CLARIFICATION — 2026-10-03
Official placement requires an authorized Employer or permitted workforce operator confirming the Student started employment. Scheduled starts remain pending_start; retention milestones remain separate. Recording a hire alone does not establish started employment. Historical and scoped official counts require explicit confirmation evidence. Existing active/ended status values and PLACEMENT_CREATED / PLACEMENT_STATUS_CHANGED audit vocabulary remain; no retention status is a placement status. Role, evidence, reporting, legacy-history and verification details: docs/D10_OFFICIAL_PLACEMENT.md (#202).

KYU/AuthCard sandbox (owner approved 2026-10-07, #257): active users own encrypted candidate-entered reusable information and named-workspace access grants. Only platform status is shared. Stripe raw verification data is never redistributed, and ordering-workspace information stays internal to TXKPRO. Fixed Authenticate mock fixtures only; no real-person screening. Full contract: docs/governance/AUTHCARD_STAGING.md.

APPENDIX C — OWNER APPROVED 2026-10-07
Employer screening policy: platform owns immutable policy versions; Employer-scoped acceptance is written by the server for an active authorized owner/admin. Private evidence has no direct API-role table grants; Candidate authorization remains separate. Contract: docs/governance/AUTHCARD_STAGING.md.

APPENDIX D — W12-20 OWNER APPROVED 2026-10-12 (#59)
Profile/community posts are owned by their natural-person Workforce author in the canonical wf_profile_posts store. Comments, reactions, shares and reposts are owned by their acting user and attributable to that active account. Direct table mutation remains denied; server RPCs derive actor identity from Auth plus an active Workforce membership.
Public feeds read only published/public post records and curated public bylines. Private profile status suppresses the profile link and headline but does not erase the minimum display-name/avatar byline approved for a public post. Profile activity controls are presentation preferences; hiding all activity or an individual category never deletes canonical interaction or audit records. Private Workforce workflow events, application data, readiness, interviews, retention/cases, notes and Employer-private data are never social-content sources.

APPENDIX E — W12-18 / W12-19 / W12-21 PUBLIC TRUST — OWNER APPROVED 2026-10-13 (#57, #58, #60)
Employer Owners/Admins and Institution Super Admins/Admins manage only their own curated organization public page. Public location, service area, programs/hiring focus, website and contact action are explicit publication inputs; they are not inferred from private Workforce records. Approved/active organization state remains a server-side publication prerequisite.
Eligible reviewers own one canonical review per Educator profile and may revise it unless it has been removed. Reviewer role and relationship are server-derived. TXKPRO platform administrators own moderation status; profile owners own only review/rating display preferences. Public summaries derive solely from published reviews.
Sitemaps, metadata, share previews and structured data read only canonical publishable projections. Private and unpublished records are excluded and noindexed.

APPENDIX F — ADS-01 OWNER APPROVED 2026-10-16 (#265, #275)
Advertiser, campaign, creative, review, funding authorization and delivery evidence are owned by the platform advertising domain. They are not Institution- or Employer-tenant workforce records and grant no candidate, hiring or Student access.
ADS-01 targeting is limited to declared coarse attributes: role family, content topic, broad geography when separately approved, and public group/context. Delivery may use only a public published content context. Messages, private groups, private Workforce records, private profile fields, applications, screening, referrals, interviews, placements, retention, notes and inferred sensitive traits are prohibited advertising inputs.
Direct approved inventory is selected first. External-network no-fill remains disabled until ADS-04 has an approved provider, data-sharing contract and credentials. Delivery evidence stores stable IDs and bounded coarse context, never private content or message text.

APPENDIX G — ADS-02 OWNER APPROVED 2026-10-16 (#264, #276)
Advertiser team membership is canonical to wf_advertiser_memberships and scoped by advertiser_id. It is deliberately not copied into app_role_memberships. Hostnames, client role labels, invitation email, URL parameters and campaign IDs are never authorization proof.
Owners/Admins manage their advertiser team and campaign lifecycle. Creative members manage drafts only. Analysts receive read-only advertiser-scoped aggregate analytics. Every mutation re-derives the authenticated user and advertiser scope in a security-definer RPC; cross-advertiser access fails closed and direct table grants remain revoked.
Self-registration creates an active advertiser and active Owner membership without platform approval; advertiser-domain access still grants no Workforce role. Stripe sandbox checkout funds an advertiser-scoped account-credit ledger. Campaign submission atomically reserves the full budget from available credit before review. Platform Admin approval—not advertiser registration—gates publishing and delivery. Rejection or requested changes releases the reserved, unspent amount to reusable advertiser credit; it does not automatically refund Stripe. Actual spend remains append-only reconciliation evidence and cannot be inferred from budget.

APPENDIX H — ADS-03 OWNER APPROVED 2026-10-16 (#265, #277)
Advertising analytics are advertiser-scoped aggregate projections. They may expose campaign, creative, placement, provider, date, valid delivery counts and distinct signed-in reach, but never viewer identities, anonymous-user inference, private Workforce fields or private-content context.
Invalid traffic and provider reconciliation append correction evidence and audit events; original served, viewable and clicked records are immutable. Invalidated delivery groups are excluded from valid performance totals. Actual spend derives only from replay-safe provider reconciliation/ledger evidence. Budget and allocation are ceilings and cannot be converted into spend from impressions, clicks or elapsed time.

ADS-04 MGID JSON integration (owner approved 2026-10-20, #278): external fallback is permitted only after direct no-fill in an approved public context, with server-only feed credentials and independent provider/filter/production gates. Required IP, user agent, language, public page path and placement are shared transiently with MGID; private Workforce records, query parameters and user identity are prohibited. No raw IP/UA is persisted. External delivery/event records belong to the platform advertising domain and remain separate from advertiser-funded campaign budgets. Canonical signed-in reports use the community moderation queue. Exact contract and approved exclusions: docs/integrations/mgid-json-native-feed.md.

ADS-04 three-item policy (owner approved 2026-10-20): sponsored units require >=3 currently displayed organic records in the relevant posts/events/polls/articles/comments list; fewer items never authorize a request or display. Three distinct public records and public group context are revalidated server-side before any ad selection. Article text or poll answer choices alone do not count. Staging-only sample content is explicitly fictional, noindex and organization-origin (no points), authored by the pre-existing Demo Student fixture identity. Owner confirms MGID exclusions applied; staging filter gate may be enabled. Production remains separately gated.
