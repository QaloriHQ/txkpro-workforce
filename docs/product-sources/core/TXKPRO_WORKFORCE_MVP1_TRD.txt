1. PURPOSE

This TRD translates the TXKPRO Workforce MVP1 PRD into an implementable technical architecture.

SOURCE-DERIVED REQUIREMENTS
The product behavior is derived from the five supplied TXKPRO Workforce documents.

EXISTING PROJECT IMPLEMENTATION CONTEXT
The current implementation already uses:
- Next.js / TypeScript;
- GitHub / Codespaces;
- Supabase Auth + Postgres;
- one shared TXKPRO Supabase project;
- server-side role resolution;
- SMS-oriented workflows compatible with Twilio.

Those stack choices come from the existing project implementation context, not from the uploaded source documents.

2. TECHNICAL GOALS

TG-01 Secure multi-role authentication and onboarding.
TG-02 Tenant- and role-scoped authorization across institutions, cohorts, employers, students, and admins.
TG-03 Instructor skill verification is authoritative and auditable.
TG-04 Deterministic, explainable talent filtering.
TG-05 Referral -> interview -> hire -> retention workflows.
TG-06 Reliable Day 30/60/90 SMS scheduling/processing.
TG-07 Pilot-scale support for roughly 1,000 students and 25 employers without architectural redesign.
TG-08 Forward-compatible foundation for PRO Points, branded tenant subdomains, SSO, and multi-campus expansion.

3. NON-GOALS

MVP1 will not implement:
- autonomous hiring decisions;
- black-box candidate scores;
- custom ML/AI candidate ranking;
- enterprise SAML/SSO;
- HRIS integrations;
- custom enterprise APIs;
- raw DMV/background/drug-test storage;
- in-platform subscription payments;
- full gamification economy;
- wildcard tenant subdomain routing as a launch dependency.

6. TENANCY AND AUTHORIZATION MODEL

6.1 CANONICAL IDENTITY
Supabase auth.users.id (UUID) is the auth identity.
Application user has a stable internal ID linked to auth.users.
A person may hold multiple role memberships.

6.2 LOGICAL ROLES
- student
- educator
- institution_admin
- employer_user
- employer_admin/owner
- txkpro_admin

If the live schema uses different names, map to the existing canonical vocabulary rather than adding duplicate role systems.

6.3 SCOPES
- platform
- institution
- program
- cohort
- employer

Example:
Educator A = educator + Program Electrical scope.
Recruiter B = employer_user + Employer ABC Electric scope.

6.4 RLS PRINCIPLES

RLS-01 Authenticated alone is insufficient; row access requires ownership/scope.
RLS-02 Student can access permitted own profile fields.
RLS-03 Educator can view/verify only assigned institution/program/cohort.
RLS-04 Institution admin can access institution-scoped placement data.
RLS-05 Employer can access only permitted discoverable talent and its own private hiring activity.
RLS-06 TXKPRO admin gets platform operations scope with audit requirements.
RLS-07 Never use user-editable auth metadata for authorization.

10. TALENT FILTERING ENGINE

MVP1 uses deterministic SQL/application filters.

Pipeline:
1. candidate is discoverable;
2. candidate belongs to employer-authorized program/cohort;
3. graduation/hire timing matches;
4. required verified skills match;
5. readiness fields match explicit criteria;
6. shift/work-type matches;
7. optional referral-only flag.

Output:
- candidate list;
- visible match criteria;
- provenance labels.

Not allowed:
- hidden employability score;
- automatic rejection;
- inferred protected/sensitive-trait ranking.

11. VERIFIED SKILLS IMPLEMENTATION

Source of truth:
Verified state is separate from self-attestation.

12. CSV ROSTER IMPORT

Flow:
UPLOAD -> PARSE -> VALIDATE -> PREVIEW -> CONFIRM -> COMMIT -> INVITE/LINK

Required fields:
- first name
- last name
- email
- program/cohort context

Optional:
- phone
- graduation date if not inherited

Validation:
- type/size
- duplicate email
- malformed email
- required fields
- unknown cohort
- existing account linkage

Idempotency:
Repeated upload must not duplicate application users or cohort membership.

Audit:
Store import job summary, actor, counts, and errors.
Do not retain original source file longer than operationally necessary unless explicitly required.

13. INTERVIEW REQUEST MESSAGING

Server flow:
1. authorize employer;
2. authorize student visibility;
3. create interview request;
4. audit;
5. send notification.

SMS only if:
- phone exists;
- SMS consent exists;
- user not opted out.

Fallback:
- in-app
- email

If direct inbound SMS is used, map response safely to an active request. If multiple requests create ambiguity, use a secure authenticated response link.

14. RETENTION PULSE DESIGN

14.1 Schedule creation
On active hire:
create hire_date + 30, +60, +90 milestones.

14.2 Scheduler
Run at least daily; hourly if operationally simple.

Select:
status='pending'
AND scheduled_for <= now()
AND placement is active.

14.3 Idempotency
Before sending:
- atomically claim/update milestone;
- do not send already sent/responded/skipped;
- persist provider message ID.

14.4 Message
Example:
“How is the job going? Reply 1 = Going well, 2 = Okay, 3 = I need help.”

14.5 Inbound webhook
- validate provider signature;
- normalize sender;
- parse supported response;
- map milestone;
- persist raw + normalized value;
- open case if at risk;
- acknowledge safely.

14.6 At-risk
Score 3:
- open case;
- notify authorized institution/TXKPRO users;
- no automatic employer action;
- human intervention process.

14.7 Consent
Maintain:
- sms_consent_at
- consent_source
- opt_out_at
- status

Honor STOP/unsubscribe immediately for the relevant messaging category.

15. DAILY ENGAGEMENT DESIGN

MVP1:
- one item/student/program/date;
- safety question OR readiness pulse;
- one response per student/item;
- streak update transaction;
- centralized timezone policy.

Anti-gaming:
- reloads cannot create multiple completions;
- streak does not alter skill verification or eligibility.

No prizes/raffles in MVP1.

D-10 APPROVED CLARIFICATION — 2026-10-03
Official placement requires an authorized Employer or permitted workforce operator confirming the Student started employment. Scheduled starts remain pending_start; retention milestones remain separate. Recording a hire alone does not establish started employment. Historical and scoped official counts require explicit confirmation evidence. Existing active/ended status values and PLACEMENT_CREATED / PLACEMENT_STATUS_CHANGED audit vocabulary remain; no retention status is a placement status. Role, evidence, reporting, legacy-history and verification details: docs/D10_OFFICIAL_PLACEMENT.md (#202).
